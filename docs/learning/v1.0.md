## What I practised

- **A plan before code.** Every issue started with a written plan that named modules, types, design choices, tests and size. Critical work waited for approval (D-62, D-72, D-80). Most plans became numbered decisions in the KB log, from D-1 to about D-489.
- **A rewrite, not a move.** The old private code served as reference only (D-59), and golden files were built fresh (D-60). The import loops in the old modules made the dependency map show quickly that moving them would cost more than writing anew.
- **Layers that a tool enforces.** One program in layers (D-46), with `lint-imports` in CI. Five pipeline stages import only `core`. When a stage needed something from another, the design changed, never the contract.
- **Truth before rules.** Hand-written truth files for the corpus came before any extraction code (#16, D-64). Every text rule first got a regression case with the expected spoken script. The voice's real readings were measured before a rule was written, so rules exist only where the voice reads wrong (D-176, D-227).
- **Testing as a set of methods.** Unit tests, Hypothesis properties, syrupy golden files, Playwright with axe-core in three browsers, Schemathesis, a nightly speech-recognition round trip, mutation runs, the OWASP ZAP scan, and fault injection for resume and downloads. Each method came in with the first code of its kind (D-58, `.claude/rules/tests.md`).
- **Release engineering.** Trusted publishing, a version check on the tag, and the built wheel tried on three systems before anything reaches PyPI (#80).

## What worked well with the agents

- **One thread per issue, and a separate thread to review it.** Review threads found real bugs:
  - a citation read twice after a confidence interval (#208 round 1);
  - the cause of the macOS-only WebKit failures behind #205.

  An author never merged its own PR (D-68).
- **A coordinator that kept the board.** It held the lanes (at most three implementation threads, one per lane, D-375), the decision numbers, the merge order and the one-line chat updates. That let the work run in parallel without two threads editing the same files.
- **Exact fix lists in review answers.** "What was fixed, and why", plus an issue for everything deferred (D-68), made second review rounds short.
- **Measuring before deciding.** Plans that started from measurements (the voice's readings, the corpus's spaces and hyphens, hostile-PDF probes) needed fewer review rounds than plans that started from rules.

## What went wrong, and the rule I added because of it

- **Flaky browser and Windows tests blocked merges.** Rule: quarantine the same day with a linked issue, and fix everything before the release (D-374). The quarantine list was empty again before v1.0.
- **Two review threads for one issue lost context between PRs.** Rule: one review thread per issue, reused for all its PRs (D-376).
- **A KB PR closed a code PR by accident** through GitHub's closing keywords. Rule: KB PR bodies never put "closes/fixes" next to a code PR link.
- **Merges were refused** when a branch was behind main (strict "CI passed"), and merge commits are not allowed. Rule: update the branch with a merge commit, wait for CI, then squash-merge pinned to the reviewed head.
- **Golden files changed more than a fix needed** (the first "↵" rule for #118 changed 143 lines). Rule: golden files stay byte-identical unless the coordinator approves the change first.
- **Browser tests that passed on Linux failed on macOS WebKit** (plain Tab skips buttons; a test's reload raced the page's own reload). Rule: shared keyboard helpers in `conftest.py`, and wait for the page to settle before acting on it.
