# ADR-002: API first, with jobs in a separate worker

`[ADR]` · Status: **Proposed** (advisor, 8 Nov 2026) · Decider: Colin · Phase: 2 · Related: ADR-001 (evolve, don't rewrite), ADR-003 (client), ADR-005 (platforms), `audit-pdfium-thread-crash.md`

> **Superseded by ADR-007 (9 Nov 2026):** no server; a local job runner replaces the API + worker split.

---

## 1. Context

`[repo fact]`
- `web.py` (7,245 lines, 152 routes, 444 functions) mixes HTML pages, unversioned `/api/…` JSON endpoints, login (e-mail code, Google), credit, invites, admin, the guided test, file handling and **job execution as threads** (`threading.Thread` at `web.py` lines 3156/3158 for runs; 1699 for reading; 2650, 4373, 4447, 6055 for side tasks).
- Scaling today: 0–4 Fly machines; each **account is pinned to one machine** (`konto_maschine`, heartbeat every 15 s); requests are forwarded with `fly-replay`; uploads over 1 MB can't be replayed, so the page gets HTTP 409 and re-sends with `fly-force-instance-id`; files sync to Tigris after each run, every 5 min and before stop; a machine stops itself after 10 min idle (`leerlauf.py`); up to 3 runs per machine (`SCI2AUDIO_LAEUFE_JE_MASCHINE`), max 4 machines (`SCI2AUDIO_MASCHINEN_HOECHSTENS`).
- Rate limiting for LLM calls is per process (`auslastung.Gate`: 4 → 2 → 1 parallel calls after HTTP 429, recovers after 8 clean calls; patience 900 s), so not global across machines.
- Sessions are cookie-based; no token auth exists.
- PDFium is used from several threads without a lock (crash risk).
- `deploy` restarts the process, which interrupts running jobs (they resume, but users wait).

`[session decision]` Future apps for Android and iOS (F-03); no users yet (F-05).

## 2. Decision

Introduce three separately runnable parts on top of the unchanged core:

| Part | Responsibility | Never does |
|---|---|---|
| **API server** (`/api/v1`) | Authentication, accounts, credit, uploads (registering files), estimates, starting/cancelling/pausing jobs, progress, results, player data, admin API | Process documents, call LLM/TTS providers, hold PDFium |
| **Job queue** (Postgres table) | Durable list of jobs with state, priority, owner, attempts, lease | — |
| **Worker(s)** | Claim jobs, run the pipeline (extract → pre-analysis → rewrite → TTS → encode), write results to storage, report progress | Serve HTTP to users |

Plus page routes for the public site (server-rendered), which stay in the web process.

```
Clients: public site (server HTML) · web client (TS) · iOS/Android app · local mode/CLI
            │
            ▼
API server  /api/v1   (FastAPI, OpenAPI spec, tokens for apps, cookies for web)
            │  inserts job                        ▲ reads progress
            ▼                                     │
Job queue (Postgres) ──claim──► Worker(s): Python core (one job per process)
                                       │
                                       ├──► Storage: Postgres (accounts, runs, credit) + Tigris (files)
                                       └──► External: Anthropic (AI text), Azure (voices), Stripe via API
```

## 3. Design details `[advisor proposal]`

### 3.1 API conventions
| Topic | Convention |
|---|---|
| Base path | `/api/v1/…`, English resource names: `/api/v1/files`, `/api/v1/runs`, `/api/v1/runs/{id}/progress`, `/api/v1/estimates`, `/api/v1/credit`, `/api/v1/account`, `/api/v1/voices`, `/api/v1/admin/…` |
| Spec | OpenAPI generated by FastAPI; committed to the repo (`openapi.json`) and diffed in CI so breaking changes are visible |
| Versioning | Additive changes within v1; breaking changes need v2; apps in stores can't be force-updated, so v1 must live as long as the oldest supported app |
| Auth | Web: secure, HttpOnly, SameSite cookie session (as today). Apps: short-lived access token + refresh token issued after the e-mail-code login; tokens revocable per device in the account page |
| Errors | One JSON shape: `{ "error": { "code": "credit_insufficient", "message": "…", "details": {…} } }`; machine-readable codes; human text localised by the client |
| Money endpoints | Idempotency key header on anything that charges or credits (`POST /runs` with a paid option, top-up confirmation); amounts in integer cents |
| Progress | Polling first (`GET /runs/{id}` with `phase`, `percent`, `eta_seconds`), as today. Server-sent events later if polling load matters |
| Uploads | Phase 2a: through the API as today. Phase 2b: presigned upload directly to Tigris (`POST /files` returns an upload URL), which removes the >1 MB replay problem entirely |
| Client-side voices | Thorsten-in-browser and device voice keep their planning endpoints (phonemes, segments) under `/api/v1/voices/…` |
| Pagination | Cursor-based for lists (runs, bookings, admin users) |
| Old routes | Stay until the new client replaces them (ADR-001); German page URLs for the public site stay for SEO |

### 3.2 Job queue
| Topic | Design |
|---|---|
| Storage | Table `jobs` in the existing Postgres (Neon): `id, account_id, kind, payload jsonb, state, priority, attempts, lease_until, worker_id, created_at, started_at, finished_at, error` |
| Claiming | `SELECT … FOR UPDATE SKIP LOCKED` ordered by priority, created_at; lease (e.g. 60 s) renewed by heartbeat; an expired lease returns the job to the queue (crash recovery) |
| States | `queued → running → done / failed / cancelled`, plus `paused`; mapped from today's phases (`fertig`, `fehler`, `abgebrochen`); stored values migrated with a read path that accepts both (glossary §4) |
| Priorities | Today's `auslastung.Priority` rules carry over: normal runs before pre-analysis jobs before batches |
| Checkpoints | Reuse today's per-chunk JSON checkpoints, so a re-claimed job resumes where it stopped |
| Cancellation | API sets `cancel_requested`; worker checks at safe points (as today) |
| Local mode | Same code, with SQLite and an in-process worker loop (single user) so local mode keeps working without Postgres |

### 3.3 Workers
| Topic | Design |
|---|---|
| Process model | One job per worker process (fixes PDFium thread-safety by construction); N worker processes per machine as memory allows (2 GB VM: likely 1–2) |
| Fly layout | Fly **process groups** in `fly.toml` (`[processes] web = … worker = …`): web machines and worker machines scale separately; workers stop themselves when the queue is empty (the idle logic from `leerlauf.py` moves here) |
| Files | Workers fetch inputs from Tigris and write outputs back; no local disk ownership, so **`konto_maschine` pinning and `fly-replay` become unnecessary** (big simplification of `maschinen.py`) |
| Global rate limit | LLM concurrency and 429 backoff state move from the in-process `Gate` to Postgres (a row per provider with a token count and a `retry_after`), shared by all workers |
| Cost cap | Workers enforce a per-run maximum cost (roadmap item 3, `--max-kosten`) and a global daily spend cap |
| Deploys | Web deploys no longer interrupt jobs; worker deploys drain: stop claiming, finish or checkpoint, exit within `kill_timeout` (120 s today) |

### 3.4 Database migrations
Schema is created in code today (`CREATE TABLE IF NOT EXISTS`, 30 tables). Introduce versioned migrations (Alembic, or numbered SQL files with a `schema_version` table) **before** adding the `jobs` table, so every later change is explicit and reversible.

## 4. Migration path (strangler pattern)

| Step | Change | Done when | Reversible |
|---|---|---|---|
| 0 | Behaviour freeze: full pytest + sample PDFs + sync test green on `main`; PDFium lock in place | `main` green; gates in `deploy.sh` and CI | — |
| 1 | Introduce migrations; add `jobs` table | Migration runs on staging and production | Yes |
| 2 | Extract run execution from `web.py` threads into a worker entry point (`python -m sci2audio.worker`); the web process enqueues instead of starting threads; same API responses | All runs go through the queue; tests green; old thread start sites deleted | Yes (feature flag `SCI2AUDIO_WORKER=on/off` during transition) |
| 3 | Move reading/pre-analysis (`markdown()` reading threads) into worker jobs | No PDFium in the web process | Yes |
| 4 | Global rate limit and cost cap in Postgres | Load test with fake 429s (`SCI2AUDIO_FAKE_429`) across 2 workers | Yes |
| 5 | `/api/v1` endpoints for every action the new client needs, generated OpenAPI committed | Contract tests per endpoint; old endpoints untouched | Yes |
| 6 | Token auth for apps | Device tokens issued and revoked; tests | Yes |
| 7 | Remove `konto_maschine` pinning and `fly-replay` once files live only in Tigris | Multi-machine test passes without pinning | Partially |
| 8 | After the new client switch (phase 3): delete old HTML-in-Python and `app.js` routes | No old surface in use | — |

Each step is one or a few PRs, `risk:high` where money, auth or data is touched.

## 5. Options considered

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| **Postgres queue + worker processes (chosen)** | No new service; Neon already in use; transactional with credit and runs; crash recovery via leases; fixes PDFium by process isolation | Polling latency (seconds, fine for long jobs); more DB load (negligible at this scale) | **Chosen** |
| Keep threads in the web process, add a lock | Smallest change | Deploy interrupts runs; one bad job can take the web server down; no global limits; apps still lack an API | Rejected as end state (lock is the phase 0 stopgap) |
| Redis + Celery/RQ/Dramatiq | Mature task frameworks | Extra service to run and pay for; another failure point; Celery complexity for a solo founder | Rejected for now; revisit at >10 workers |
| Managed queue (e.g. SQS, Cloud Tasks) | Scales | Vendor sprawl beyond Fly + Neon + Tigris; GDPR processor list grows | Rejected |
| Serverless functions for pipeline steps | Pay per use | Long jobs (minutes to hours), large binaries (Tesseract, ffmpeg, PDFium, ONNX), cold starts | Rejected |
| Microservices (separate extraction/TTS/rewrite services) | Independent scaling | Network boundaries inside one pipeline; much more ops for one person | Rejected |
| GraphQL instead of REST | Flexible queries for clients | More machinery; caching and file uploads awkward; OpenAPI tooling for mobile is simpler | Rejected |

## 6. Consequences

**Positive:** apps become possible; deploys stop interrupting runs; PDFium crash class removed; global rate limits and cost caps become enforceable; machine pinning and replay logic disappear; the API contract (OpenAPI) is a testable spec.

**Negative:** phase 2 is the largest refactor (several weeks of PRs at the WIP limit); two code paths during the transition (feature flag); new operational piece (worker group) to monitor; more Postgres dependency (Neon availability now matters for every run).

## 7. Revisit triggers
- Queue polling becomes a measurable cost or latency problem → consider `LISTEN/NOTIFY` or a dedicated queue.
- Workers need GPUs (e.g. own TTS model server-side) → separate GPU worker pool.
- Neon cold starts hurt interactive latency → keep one compute warm or move Postgres.
