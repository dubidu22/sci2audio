## Must fix

**M1. The read-along shows edits of plugins that did not make the audiobook.** `player_for` (`player.py:1135-1137`) uses the server's plugin steps whenever the record does not say `plugins: false`, and ignores the plugin list #669 puts in the record. Probe: an audiobook made on a server with no plugin (voice spoke "Salt & pepper are on the table."; `audio.json` has no `plugins` key), then the same work folder opened by a server whose runner has the ampersand plugin: the Listen page renders a `said` span ("&" shown as read "and") the voice never said. The same happens after any plugin is installed, upgraded to change its edits, or added next to the ones the book was made with. This is what D-847 ordered the PRs to prevent ("the read-along cannot show plugin edits that were never spoken"). Fix at the root: `AudioRecord` reads the record's `plugins` ids (absent = none), and `player_for` keeps only the plugin steps whose id the record names (built-in steps always). That replaces the plan's "older records read as plugins on": plugins exist only in Unreleased (#216), so no released record was made with one, and a record without the list honestly says no plugin made it; `settings.plugins: false` then needs no special case. A record that names a plugin the server no longer has can still only show the built-in edits; a one-line notice there is optional. Because it changes an approved plan line, the coordinator records the change. Tests: the probe above as a test (book made without plugin, plugin installed later → no plugin edit shown), and a book made with the plugin → its edit shown (T14 stays).

**M2. The privacy page says "No text-step plugins are installed." while one is installed and its code has run.** `pages.py:1351` passes only `state.runner.steps.plugins`, the plugins that loaded; the template (`privacy.html:29`) prints `plugins_none` when that is empty. A package whose entry point fails to load (wrong `api_version`, a missing name, an exception in its factory) is installed, had its import code run with the program's rights, and appears in `runner.steps.problems`, yet the page says none is installed. Probe: an entry point `example_text_plugin:NoSuchThing` → one `PluginProblem`, privacy page: "No text-step plugins are installed." On the page that tells a person whether other people's code runs inside sci2audio, that sentence must not be false. Fix: pass `problems` too, list them ("Installed but not loaded: id (distribution): reason", both languages), and show `plugins_none` only when both are empty; extend T19 with a failing entry point.

## Should fix

**S1. "Installed now" and "uninstalling switches it off" leave out the restart.** The server's runner loads the plugins once at start (`JobRunner()` in `create_app`), so after uninstalling (or installing) a package the running interface still runs (or does not run) it until sci2audio is restarted, and "Installed now:" (`privacy.plugins_installed`) shows the start-up list. Failure scenario: a person reads the privacy page, uninstalls a suspicious plugin, starts the next job in the same interface session, and the plugin runs. Say "Loaded when sci2audio started:" / "Beim Start von sci2audio geladen:" and "uninstalling a plugin's package and restarting sci2audio switches it off in the interface" in both tables and the README; extend T20 to look for the restart.

**S2. The privacy text shows raw Markdown backticks.** `privacy.plugins` in both tables wraps `sci2audio.text_steps`, `sci2audio script --no-plugins` and `sci2audio convert --no-plugins` in backticks; `t()` escapes text and has no Markdown, so the page shows the backticks literally, the only page string that does (screen readers may read them out). Either drop the backticks or put the entry-point name and the commands in `<code>` from the template (e.g. placeholders filled with `<code>` elements, as the update-host line does); T20 keeps working on the plain names.
