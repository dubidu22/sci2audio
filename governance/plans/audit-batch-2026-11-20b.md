### Should-fix

**F1 (should-fix). Plugin code still runs in the job's thread through the exception `find` raises, and #693 does not name it.** `_GuardedStep.find` re-raises a plugin's `Exception` object as it is (`textprep/plugins.py:353-354`). The runner then formats it in the job's thread with `f"{type(error).__name__}: {error}"` (`textprep/runner.py:152`, strict: `:151`), which calls the plugin's `__str__` with no time limit and outside any `try`. The `SystemExit` and `BaseException` branches format in the caller too (`plugins.py:356` `error.code!r`, not caught at all; `plugins.py:358` `_said`, which catches a raise but not a hang). Probe at b00002d: a plugin whose `find` raises an `Exception` subclass with a raising `__str__`. `run_steps(..., strict=False)` raised `ValueError` out of the run, and `__str__` ran in `MainThread`. With a `__str__` that blocks, the job hangs for good. A careless plugin hits this with a lazy-translated message, against #216 criterion 2 (one plugin never stops a job). Related: the copy `given` is made and dropped in the job's thread, so a `__del__` of an object the plugin planted in it runs there too (a variant of #693's first point). So #693 names two places (the copy comparison and the returned edits) but not all of them; the exception path is the third. Import-time side effects (atexit handlers, threads, monkeypatching) are in-process by design, and the privacy page says so. `docs/plugins.md:99` says the plugin's import, factory, attributes and `find` run in a worker; that holds for the calls, not for the objects they return or raise. Fix: no plugin object crosses `_in_worker`. In the worker, turn what the call raised into a plain `StepError` whose message `_said` builds there, and make, compare and drop the copy in the worker as well. Edit to #693 and the META-03 check below.

**F2 (should-fix). The promised-tests check (#692, #707) passes a plan PR that promises nothing it checks.** The check is opt-in by the exact heading. Without it, `.github/governance/promised_tests.py:129-136` prints "no section (opt-in)" and passes. `NEAR_RE` (`:35`) catches only variants of the words "tests promised in (the) plan". This already happened once. #689 merged at 19:24Z, 15 minutes after #692 (19:09Z). Its body has a plan (`web-b-w2-plan.md`) and 16 backticked node IDs (T1 to T11 plus the round-1 tests) under `## Plan tests`, which the check passes as absent at b00002d too (probe). The node IDs do collect (probe), so nothing was lost this time. Failure scenario: a plan PR drops a promised test and lists its tests under `## Tests`, and the check stays green. A second weakness: promises are checked only for presence, so a section that lists only tests that were already on `main` passes. The near-miss rule itself has no false positives: run on the last 15 merged bodies (`gh pr list --state merged --limit 15`), none fails. All five exact sections (#690 #692 #696 #698 #707) are read with nothing unreadable. Fix: fail when the body holds a backticked `tests/...py::name` outside fences but no exact heading. On the sample this flags #689 and the pre-rule bodies #671 #675 #691, which PLAN-01 (D-849) now requires to carry the heading anyway, and no docs or Dependabot body. Also print, without failing, the promises that already collect on the base, so the reviewer sees which ones are old.

## META-03: the recurring "unguarded-plugin-code" finding

Seen in #676 (round 1 S1, and audit F1 of batch 1: loading unguarded), in #690 (round 1 M1: attribute checks in the caller's thread), in #693 (run-time results) and here (F1: the raised exception). Each fix closed the path its review found, and the next review found another. Reviews cannot keep up with this kind, but one test can.

**Proposal: a hostile-plugin test that records the thread every plugin-supplied object runs in.**

- Location: `tests/unit/test_textprep_plugin_isolation.py` (about 150 lines), with a tracer helper of about 60 lines added to `tests/unit/broken_text_plugins.py`.
- The tracer: a mixin whose dunders (`__str__`, `__repr__`, `__format__`, `__eq__`, `__ne__`, `__hash__`, `__lt__`, `__bool__`, `__len__`, `__iter__`, `__index__`, `__int__`, `__getattr__`, `__del__`) append `threading.current_thread().name` to a shared list before they answer. It is applied to `str`, `int`, `tuple`, `list`, `Exception` and `Edit` subclasses and to a plain object.
- The plugin, parametrised over every hand-over point: the id and languages; the factory's result; the exception `find` raises (`Exception`, `SystemExit` with a tracer code, a `BaseException`); the returned list and its `Edit`s; the span offsets and the replacement text; and an object planted in the document copy.
- It drives the real path: `installed_steps(entry_points=[...], load_timeout=0.5)`, then `run_steps` both strict and non-strict, then the report text (`app.report.plugins_line` and the problems).
- The assertion: every recorded thread name starts with `loading text step ` or `text step ` (the names `_in_worker` gives), and the run ends with a `StepProblem`, not an exception.
- Cost: under 1 s in the fast suite. It fails on b00002d (F1 and #693), so it lands as the first, failing test of the #693 PR, which then makes it pass with the design change of F1. With that change no plugin object crosses `_in_worker`: the worker returns plain `str`, `bool` and rebuilt `Edit`s, and raises only `StepError`. This is the strongest rung META-03 allows here. The test proves the property for every hand-over point at once, and a later path that leaks a plugin object fails it without a reviewer having to spot it.
