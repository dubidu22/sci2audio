## Findings

### Must-fix

- **M1 (kind: unsound-guard).** `.github/workflows/governance-pr-checks.yml:60` (and its copy): the gate step runs *last*, after two steps that execute the PR's own code in the same job: `python3 .github/governance/pr_checks.py` (line 32, from the PR checkout) and `uv run --frozen pytest --collect-only` (line 47, which imports the PR's `conftest.py` and test modules whenever the body has the promised-tests heading, and the PR writes the body). Code that runs there can append to `$GITHUB_PATH` or `$GITHUB_ENV`, rewrite `.git/config`, or use the runner's passwordless `sudo` to replace `python3` or `git`, and so decide the verdict of the later gate step without touching the workflow file. `tests/conftest.py` is not on `critical_paths`. So the guarantee the step's comment (line 62: "so a PR cannot change its own verdict"), the plan and the PR body state ("a PR cannot change the code that judges it"; the only residual named is editing the workflow file) does not hold as built. `test_the_governance_check_gates_a_risk_high_pr_on_the_ledger_of_branch_governance` pins exactly this order ("the gate is the last step", `tests/unit/test_ci_workflows.py:455`). The fix is cheap: once the step runs before any PR code, the only remaining way is editing the workflow, as stated.
  - **Fix wanted:**
    1. Move the step "Check that a risk:high PR has an approving review round for its head" to directly after the `actions/checkout` step, before "Check title, labels, ownership and critical paths". Keep its `if: ${{ !cancelled() }}`.
    2. Give "Check title, labels, ownership and critical paths" `if: ${{ !cancelled() }}`, so it still runs when the gate step fails (today it has no `if` and would be skipped).
    3. Make the same change in `governance/github-setup/pr-checks-workflow.yml` (byte-equal).
    4. In the test, replace the "last step" assertion: the gate step is the first step after the checkout step, and it comes before every step whose `run:` executes repository code (the `pr_checks.py` and `uv run` steps); and the title step carries `if: ${{ !cancelled() }}`. Check the new assertion is red on the current order.
    5. Reword the step comment and the PR body's "Not covered" so they say: no PR code runs in the job before the step; the residual is a PR that edits this workflow file (and S4).

### Should-fix

- **S1 (kind: weak-guard).** `governance/tools/ledger_tool.py:384` and `:377` (`approved`): the head comparison is `same_head`, a prefix match of 7 or more characters. CI passes the full 40-character `PR_HEAD`, and the README's examples (`head: 3f9c2ab`, lines 54, 80, 94) invite short SHAs in round entries and overrides. A 7-hex prefix (28 bits) is cheap to collide, so a commit pushed after the approval whose SHA starts with the recorded short head would pass the check. For the check CI relies on, require the exact full SHA.
  - **Fix wanted:** in `approved`, accept a round's `head`/`updated_head` or an override's `head` only when it is 40 hex characters and equal (case-insensitive) to `--head`; for a shorter recorded SHA say so in the reason ("record the full 40-character head for the governance check"). Make the CLI require 40 hex characters for `approved --head`. In `ledger/README.md`, say that `head` and `updated_head` of a round entry (and an override's `head`) are the full SHA. Add the short-head and full-head cases to `test_approved_passes_only_the_head_the_latest_round_approved`. `gate` may keep `same_head`.
- **S2 (kind: missing-test).** `tests/unit/test_ledger_tool.py`: nothing runs `ledger_tool.py approved` as CI does (the CLI: `--ledger`, exit codes 0, 1 and 2). The workflow test checks only the command string, and the functions are tested in-process. A change in `main()` (argument names, exit codes) would pass all tests and break, or open, the required check.
  - **Fix wanted:** one test that writes a small ledger in `tmp_path` (one PR entry, one approving round) and runs `python3 governance/tools/ledger_tool.py approved 12 --head <sha> --ledger <dir>` with `subprocess`, asserting exit 0 for the approved head, 1 for another head, 2 for a missing or malformed `--head`, and 2 for a missing ledger directory.
- **S3 (kind: missing-test).** `governance/ledger/README.md`: the plan says the refresh rewrites this file from the skill's copy "so the hand changes there are guarded by tests too", and the PR body says the skill's copies lack these changes. The tool and `dispatcher_instructions.md` are guarded; the README's `gos/` row and format, `merged` in the PR format, `updated_head`, and the `approved` command are not, so a refresh drops them silently.
  - **Fix wanted:** in `tests/unit/test_ruleset.py` (beside `test_the_dispatcher_instructions_carry_the_d882_changes`), assert the README holds the `gos/pr-<N>.yaml` writer row, the `gos/` format block, the PR format's `merged:` line, the round format's `updated_head:` line and the `ledger_tool.py approved` usage line.
- **S4 (kind: incomplete-residual-risk).** PR body "Not covered": PRs into `release/1.0`, `release/1.1` and `release/1.4` (all exist) run their branch's own `governance-pr-checks.yml`, which has no gate step, so a `risk:high` release fix (REL-01) is not gated until the step reaches that branch. The body should say so.
  - **Fix wanted:** name it in the PR body's "Not covered", and open an issue (GH-01, milestone, `lane:infra`, `risk:high`) to bring the step to the release branch that is still served (the next release-branch PR, or a port under REL-01), or to record that release PRs stay ungated.
